# 04-打卡日历与统计

## 目标

为绑定双方提供一个可视化的坚持情况总览：用户可以在一个页面看到自己的打卡日历、连续签到天数、积分趋势和最近记录统计。解决目前积分和签到数据散落在流水表里、没有任何可视化呈现的问题。面向两个绑定用户，管理员视角可以查看绑定对象的同款统计。

## 接入模块

| 层 | 位置 | 说明 |
|---|---|---|
| 前端主模块 | `frontend/src/features/stats` | 新增 feature，包含日历视图、统计卡片、积分趋势图。 |
| 后端主模块 | `backend/src/main/java/com/formygirl/stats` | 新增只读统计模块，仅做聚合查询，不写任何业务表。 |
| 协作模块 | `points`（读取 POINT_LEDGER 签到与积分流水）、`record`（读取 DAILY_RECORD 记录条数）、`relationship`（管理员视角查看对方数据时的授权校验） | 只读复用，不修改这三个模块的任何逻辑。 |

## 用户和权限

- 使用者：当前登录用户（USER）。
- 是否需要绑定用户：默认查看自己的统计；管理员视角查看绑定对象统计时需要绑定关系。
- 对方是否可操作：不可写，纯查看。
- 后台人员是否可操作：不涉及。

## 主链路

```text
首页点击统计入口
  -> 前端 features/stats 调用 API helper
  -> 后端 StatsController
  -> Service 校验当前视角（自己 / 绑定用户）
  -> Repository 只读聚合 POINT_LEDGER、DAILY_RECORD
  -> 返回统计 DTO（日历打卡集合、连续天数、积分序列、记录计数）
  -> 前端渲染日历、连续天数、趋势图
```

## 前端影响

- 页面或组件：新增 `StatsPage`（日历 + 卡片 + 图表），首页底部或角色页增加一个"统计"入口图标。
- API helper：新增 `features/stats/api.ts`。
- DTO 类型：新增 `features/stats/types.ts`。
- 状态和错误展示：加载骨架屏，接口失败显示重试按钮；不引入新全局状态。
- 图表依赖：优先纯 CSS/SVG 实现连续天数与柱状趋势，避免引入重量级图表库。

## 后端影响

- Controller：`stats/StatsController.java`。
- Service：`stats/StatsService.java`（含视角与授权校验）。
- Repository：`stats/StatsQueryRepository.java`（只读，聚合 SQL，不使用其他模块的写方法）。
- 需要复用的模块：`relationship` 的绑定校验；`identity` 的当前用户。
- 不能耦合的模块：`record` 写链路、`points` 写逻辑、`sync`/`thirdclient`/飞书，全部不触碰。

## 数据库影响

- 新增表：无。
- 变更表：无。
- 关键索引：如聚合查询变慢，后续可对 `POINT_LEDGER(person_id, source_type, created_at)` 补充索引，本期先不加。
- 幂等或唯一约束：不涉及，纯只读。

## 外部服务影响

- 是否调用 third：否。
- 是否写飞书：否。
- 是否需要保留 payload 或错误：否。
- 是否需要 trace：否。

## 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/stats/checkin-calendar?year=&month=` | 返回指定月份的打卡日期集合、当月签到次数。 |
| `GET` | `/api/stats/summary` | 返回连续签到天数、累计积分、本月记录数、最近 14 天每日积分序列。 |
| `GET` | `/api/bound-user/stats/summary` | 管理员视角查看绑定用户的同款统计（复用 relationship 授权校验）。 |

## 统计口径

- 连续签到天数：以自然日计算，今天已签到则连续到今天，未签到则连续到昨天，中断归零。
- 每日积分序列：按 `POINT_LEDGER` 当日发生额汇总（含签到、打分、差额调整），负数照实计入。
- 本月记录数：`DAILY_RECORD` 按自然月计数。
- 所有口径与积分模块现有规则一致，不在统计层重复计算积分。

## 排查入口

- 前端先看：`features/stats` 的 API helper 与 DTO 映射。
- 后端先看：`StatsService` 的视角判断，再看聚合 SQL。
- 数据库先看：`POINT_LEDGER` 流水是否为空、`source_type` 取值是否覆盖签到与打分。
- 关键 ID：当前用户 `person_id`、绑定关系 `binding_id`。
